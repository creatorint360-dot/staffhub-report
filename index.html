Design and Implementation of a Secure Login System

A staff-records system with identification, two-factor authentication, role-based authorization, salted and peppered password storage, encryption and automatic backups.

Computer Security · PBIT 309 / PBSE 309 Samuel Dzenenya 19 October 2026
IntroductionArchitectureAuthentication PasswordsRolesDatabase security Cryptography & CIABackupsBalanceEvidence

1Introduction

StaffHub is a staff-records web system with a secure login. Its purpose is to make sure only genuine users get in, and that each user can do only what their job allows.

It provides user identification, two-factor authentication, role-based authorization, safe password storage with salt and pepper, a secure database connection, a local server, and a balance between security and ease of access. It also applies cryptographic techniques and automatic backups to protect confidentiality, integrity and availability.

3Identification and authentication

Identification means claiming who you are. Every user has a unique username, so each action can be traced to one person. Authentication means proving the claim. It is like giving your name at an airport (identification) and then showing your passport (authentication).

Two-factor authentication (2FA) asks for two different kinds of proof: something the user knows (the password) and something the user has (a phone with an authenticator app). An ATM works the same way: it needs the card and the PIN, so a thief with only one gets nothing.

StaffHub uses a time-based one-time password (TOTP). The phone and the server share a secret key. Every 30 seconds both combine the key with the current time and produce the same 6-digit code. A stolen code is useless a minute later.

  • After the password step the user is only "half logged in"; the dashboard stays closed until the correct code is entered.
  • Five wrong attempts lock the account for 15 minutes, which stops brute-force guessing.
  • The login message is always "Incorrect username or password", so attackers cannot discover which usernames exist.
  • If a user loses their phone, the Administrator can reset their 2FA and the action is logged.

4Password storage: hashing, salt and pepper

Passwords are never stored as plain text, because anyone who stole the database could read them all. Instead the system stores a hash, a one-way scramble that cannot be turned back into the password. Hashing is like turning a cow into a burger: it only goes one way. At login the typed password is hashed again and compared with the stored hash.

TechniqueWhat it isWhere it is keptWhat it prevents
SaltA random value added to each password before hashingIn the database, inside the hashIdentical passwords giving identical hashes; rainbow-table attacks
PepperA secret value added to every passwordIn a protected config file, outside the databaseAn attacker with only the stolen database guessing passwords

Every password goes through the same six steps, written out one by one in the code (includes/security.php):

StepWhat happensFunction
1Salt: 16 random bytes (32 hex characters), different for every usergenerate_salt()
2Pepper: one secret value read from the config fileget_pepper()
3Combine by concatenation: salt + password + peppercombine_salt_password_pepper()
4Pre-hash the combined text with SHA-256 (always 64 characters)prehash()
5Hash the result with bcrypt, cost factor 12 (deliberately slow)hash_password()
6Store as v2$salt$bcrypt-hashhash_password()

bcrypt is deliberately slow: unnoticeable for one login, but very expensive for an attacker trying millions of guesses. At login the system reads the saved salt, repeats steps 3 to 5 with the typed password, and compares the result. A password policy requires at least 10 characters with upper case, lower case, a number and a symbol.

Salt and pepper in the database. So that every step can be inspected, the users table has a column for each part:

ColumnHoldsSame for all users?
saltThe user's random saltNo, unique per user
pepperThe pepper value (shown for demonstration)Yes
salt_pepperThe concatenation of salt and pepperNo, because the salt differs
password_hashThe final stored result, v2$salt$bcrypt-hashNo
hash_methodThe recipe in wordsYes
The password itself is never stored. The concatenation column holds only salt and pepper; the full recipe is salt + password + pepper. In a real deployment the pepper would stay only in the config file, outside the database. A copy is shown in the table for demonstration, and a configuration switch turns that off.

5Authorization based on roles

Authorization decides what a logged-in user may do. StaffHub uses role-based access control (RBAC): permissions belong to roles, and people are given roles. In a hospital, a nurse's badge opens the ward but not the pharmacy store; the badge decides, not the person.

ActionInputterManagerAdminAdministrator
Add and delete own recordsYesYesYesYes
View all recordsNoYesYesYes
Delete any recordNoNoYesYes
Add an InputterNoYesNoYes
Add a Manager or AdminNoNoNoYes
Delete an InputterNoNoYesYes
Unlock accounts, reset 2FANoNoNoYes
View and clear the audit logNoNoNoYes
Change own passwordYesYesYesYes

Least privilege means each role gets only the access it needs. Separation of duties means no ordinary role controls a whole process: a Manager can add Inputters but not delete them, and an Admin can delete them but not add them. Rules are checked on the server for every page, so typing a restricted address as an Inputter returns "403 Forbidden" and the attempt is logged.

6Secure database connection and attack protection

The application connects through PDO using a limited MySQL account (staffhub_app) instead of the all-powerful root, and only from localhost. It cannot delete tables or touch other databases. The database password lives in a configuration file that the web server refuses to show. Errors are logged privately and the visitor sees only a generic message.

AttackSimple exampleDefence
SQL injectionTyping a database command into the username boxPrepared statements keep commands and data separate
Cross-site scripting (XSS)A script saved inside a recordAll output is escaped, so scripts show as plain text
Cross-site request forgery (CSRF)An evil site secretly submits a delete form using your loginSecret token in every form; SameSite cookies
Brute forceTrying many passwordsAccount lockout and slow bcrypt hashing
Session hijackingStealing the login cookieHttpOnly cookie, 15-minute inactivity timeout, new session ID after login

The audit log records logins, failures, lockouts, denied access, deletions and backups, each with username, time and IP address.

7Cryptographic techniques and the CIA triad

ConfidentialityOnly authorised people can read data: hashed passwords, encrypted records and 2FA secrets, roles, encrypted backups.
IntegrityData cannot be changed secretly: authenticated encryption, prepared statements, CSRF tokens, audit log.
AvailabilityData is there when needed: automatic encrypted backups, off-site copy, tested restore, account recovery.

Encryption. Record details and each user's 2FA secret are encrypted with AES-256-GCM before they are saved. Encryption scrambles readable text into unreadable text using a key, and unlike hashing it can be reversed with that key. The key is kept in the config file, not the database, so a stolen database shows only unreadable text. GCM adds an authentication tag, so if anyone alters the stored data, decryption fails instead of returning false information. A fresh random value is used each time, so the same text never encrypts to the same result.

8Automatic backups (availability)

Data can be lost through accidental deletion, a broken disk, ransomware or theft. Backups let the system recover.

  1. A scheduled task runs backup.php every night at 2:00 AM (Windows Task Scheduler).
  2. It exports the database using a separate read-only MySQL account.
  3. The dump is encrypted with AES-256-GCM and the readable copy is deleted.
  4. The encrypted file is saved in a protected local folder.
  5. The same encrypted file is uploaded to a private Supabase Storage bucket over HTTPS, so Supabase only ever holds unreadable data.
  6. Backups older than 14 days are deleted, and every result is written to the audit log.
  7. A restore script decrypts a backup so it can be imported, which proves the backup works.

This follows the 3-2-1 rule: three copies (live database, local encrypted backup, cloud encrypted backup), on two kinds of storage, with one off-site.

9Balancing security and access, and conclusion

A system locked so tightly that nobody can use it is as useless as one left open, and too much difficulty pushes people into risky habits such as writing passwords on paper. StaffHub keeps the strong checks at login and lets the system work quietly in the background.

  • The 2FA code is asked only at login, not on every click.
  • A lockout lasts only 15 minutes and clears by itself; the Administrator can unlock sooner.
  • The session ends after 15 minutes of inactivity, so active users are not interrupted.
  • Each role has what it needs for its job and nothing more.
  • A user who loses a phone can be recovered by the Administrator, and the action is logged.
  • Backups run automatically, so nobody has to remember them.

Conclusion. StaffHub meets the requirements by combining several layers of protection, called defence in depth: identification, two-factor authentication, role-based authorization, salted and peppered hashing, encryption, a secure database connection, audit logging and automatic encrypted backups. If one layer fails, the others still protect the data. A real deployment should also use HTTPS and a dedicated secrets vault for its keys.
